# PR #469: does a prefill sharing the step change a GDN decode row? (vLLM 0.30.0, B200)

`probe_mixed_step.py` replays, with the library kernels and synthetic inputs, the two paths `QwenGatedDeltaNetAttention._forward_core` takes for the same decode rows (vLLM 0.30.0, torch 2.13.0+cu130, one NVIDIA B200): A, decode-only step with the packed fast path (`causal_conv1d_update` then `fused_recurrent_gated_delta_rule_packed_decode`); B, decode-only with the packed path off (`causal_conv1d_update` then `fused_sigmoid_gating_delta_rule_update`); C, a mixed step (`causal_conv1d_fn` over the decode tokens and one prefill, then `fused_sigmoid_gating_delta_rule_update` on the decode rows, as the layer does after peeling the decodes off). There is no checkpoint, scheduler or attention metadata, so this shows what the kernels do, not what a served model does. Results: `results-b200.json` (decode rows 1 / 4 / 17 / 64; fp32 and bf16 recurrent state; TP1 shapes with 16 key / 32 value heads and TP4 per-rank shapes with 4 / 8). The probe was run twice, once while the GPU was shared with another job and once on an idle GPU (no other process, 0% utilisation and 0 MiB used before and after); the two result files are identical, and `results-b200.json` is the idle run.

Findings (the JSON has every case):
- C and B are bitwise identical in every case (convolution output, convolution state, recurrent state, output), and C with a 64-token and with a 1031-token prefill are bitwise identical: the result of a decode row in a mixed step does not depend on the co-scheduled prefill.
- A differs from B and C in the recurrent state and, at 64 rows, in a few outputs. With fp32 state, TP1 shapes: 55,812 of the 524,288 state elements of the single decode row at B=1, and up to 134,283 per row at B=64 (4,887,029 of 33,554,432 over 64 rows); 0 output elements at B=1 and 17 of 262,144 at B=64. With bf16 state: 2 state elements at B=1 and 390 of 33,554,432 at B=64; 23 output elements at B=64. TP4 per-rank shapes: fp32 state 39,577 of 131,072 at B=1, 2 of 65,536 outputs at B=64; bf16 state 2 at B=1, 5 outputs at B=64.
- Repeating A gives the same bytes.

So the difference is the kernel choice (packed decode vs the general fused kernel), which the layer makes depend on whether a prefill shares the step; it is not an effect of the prefill's tokens.

## Seed sweep of the single-decode-row case

`probe_mixed_step_seeds.py` runs the one-decode-row case (path A against path C) over 200 random fixtures for each shape and state dtype (`results-seeds-b200.json`, one idle B200, same software as above). The counts depend on the fixture, so a single number is not a property of the kernels:
- State elements of the one decode row that differ, out of 524,288 (TP1 shapes) or 131,072 (TP4 per-rank shapes): fp32 state, TP1: minimum 22,181, median 83,588, maximum 164,510 (200 of 200 fixtures differ); fp32 state, TP4 per-rank: 59 / 18,102 / 55,226; bf16 state: median 6 (TP1) and 1 (TP4 per-rank), maximum 18 and 7.
- bf16 output elements that differ, out of 4,096 (TP1) or 1,024 (TP4 per-rank): at TP1 shapes 38 of 200 fixtures with fp32 state (34 with exactly one element, 4 with two) and 42 with bf16 state (39 with one, 3 with two); at TP4 per-rank shapes 11 of 200 with fp32 state and 15 with bf16 state, every one with exactly one element.
